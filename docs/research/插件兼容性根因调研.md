# 为什么 DSH 发新版后大量插件就不兼容了

> 调研日期：2026-09-23
> 一手证据：本地源码 `D:\codes\deepseek-harness`（HEAD `ddefc45fbc`，version `0.1.7-alpha.2`）
> 官方仓库：`github.com/deepseek-ai/deepseek-harness`

## 一句话结论

**这不是 bug，是官方明确声明的既定策略 + 架构选择 + 缺失护栏三者叠加的必然结果。**

官方 README 原文（全大写，非免责套话）：

> DeepSeek Harness is in _developer preview_ and iterating rapidly.
> **THERE WILL BE COMPATIBILITY-BREAKING CHANGES.**

所以准确的问题不是"为什么会不兼容"，而是"**为什么一次发版会让一大片插件同时失效**"。答案分四条机制。

---

## 机制一：宿主接口改名 / 移除

DSH 是"万物皆插件"架构——工具、UI、模型适配器、会话存储、沙箱后端**全都是插件**，连内核包本身（`@deepseek-ai/cordis`、`@deepseek-ai/dsh-fs-local`、`@deepseek-ai/dsh-subprocess-local`…）都是插件 `peerDependencies` 的一部分。

内核一动，边界就是插件的边界。典型报错：

| 报错 | 含义 |
|---|---|
| `does not provide an export named …` | 插件用了已被移除/改名的 API |
| `ERR_PACKAGE_PATH_NOT_EXPORTED` | 上游未适配模块导出结构 |
| `ERR_REQUIRE_ESM` | 上游未适配模块格式 |
| `NODE_MODULE_VERSION` / `compiled against a different Node.js version` | Node 升级后原生模块失配 |

发版节奏可以参考：2026-08-10 到 2026-09-10 一个月内，官方产出 **26 个 alpha/RC tag**。

---

## 机制二：Cordis 的 `inject` 是运行期硬校验（最阴的一条）

Cordis 内核的服务访问不是普通属性读取，而是沿 fiber 树做注入查找。**插件没在 `inject` 里声明的服务，一旦碰就当场抛错**：

```
Internal error: cannot get property "agents" without inject
cannot get property "sessionPersistence" without inject
cannot get property "webServer" without inject
```

注意报错里是**属性名**（`agents` / `webServer`），**不是插件名**。所以用户看到一堆这种错，根本判断不出是哪个插件坏了——这是"感觉所有插件都坏了"的直接原因。

### 实证 1：官方 Postmortem 0001（`docs/postmortem/0001-acp-default-export-drops-inject.md`）

一个 `export default` 就能让插件崩溃。Cordis Loader 的 `unwrapExports`（`vendor/loader/src/index.ts`）：

```ts
unwrapExports(exports: any) {
  if (isNullable(exports)) return exports
  exports = exports.default ?? exports        // ← 优先取 .default
  if (!exports.__esModule) return exports
  return exports.default ?? exports
}
```

插件里多写一行 `export default apply`，unwrap 结果就变成**裸 apply 函数**——而 `name` / `inject` / `Config` 是**同级命名导出**，整个命名空间被丢弃。Loader 于是基于**空的 inject** 建 fiber，`apply` 第一行 `ctx.agents` 就抛错。

> **崩溃发生在加载时，不是在请求处理里。**

该事故的教训被官方写成了规则：**命名空间插件与 default export 在 Cordis Loader 下互斥。**

### 实证 2：0.1.7 的 `webServer` 事件（第三方补丁包 `@zhengcankai/deepseek-harness` 记录）

0.1.7 给 `@deepseek-ai/dsh-client-connection` 的 RPC 注册表加了 `webServer` 依赖，但**没有用 `ctx.inject(['webServer'])` 包裹**。后果：

> 任何调用 `ctx.connection.rpc.handle()` 的插件（例如 dsh-funny-wiki 面板）**加载失败，并 abort 整个 plugin tree**。

一个内核侧的疏忽，直接灭掉一整类 UI 插件。

## 机制三：整树加载 —— 一坏则全坏

这是"**集体**失效"的机制根源，不是"所有插件都坏了"。

`packages/boot/app-boot/src/index.ts:985` 有明确的失败标签：

```ts
stage = 'plugin tree failed to load'
```

`packages/boot/app-boot/README.zh.md:137` 官方说明：

> `boot()` 区分 `host preparation failed`（`prepare` 在任何配置树条目挂载前抛出）与 `plugin tree failed to load`，并追加最深层插件错误的堆栈。

**插件树是整体加载的。一个 entry 失败，整棵树失败。** 用户看到的现象就是"升级完，几十个插件全用不了了"，实际上可能只有一个是真凶。

---

## 机制四：静默失配 —— 装了坏插件，零告警

两边护栏同时缺失，装插件时**没有任何兼容性提示**，问题全部推迟到运行时才爆。

### CLI 侧：零 peer 校验

`apps/cli/src/plugin.ts` 全文只有 25 行，就是个 pnpm 转发器：

```ts
/** dsh plugin forwards pnpm through the shared profile package operations. */
export async function runPlugin(profile: string, args: readonly string[]): Promise<number> {
  const result = await runPluginCommand({ profile, installAnchor: INSTALL_ANCHOR, cwd: process.cwd() }, args, { ... })
```

`apps/cli/src` 全目录 grep `peerDependencies` → **0 命中**。
`apps/cli/src` 全目录 grep `doctor` / `marketplace` → **0 命中**（说明这两样都不是官方 CLI 能力）。

### pnpm 侧：peer 根本不参与解析

profile 模板硬编码（`packages/boot/app-boot/src/profile.ts:203-208`）：

```yaml
packages:
  - .

nodeLinker: hoisted
autoInstallPeers: false
```

而 host 包（`@deepseek-ai/*`）是由 **CLI 的共享根层**提供的，**不在 profile 的依赖图里**。于是 pnpm 连"unmet peer"都没机会报。

### 结论（官方 Discussion #6680）

> 对由宿主提供的 `@deepseek-ai/*` peer 来说，**声明目前实际上是装饰性的。**

实测：`dsh-win32@0.17.8` 声明 `@deepseek-ai/dsh-subprocess-local: ">=0.1.0-rc.5 <0.1.0-rc.7"`，而宿主提供 `0.1.5-rc.2`（明确冲突），`dsh plugin add` 安装输出**没有任何 warning**。

**插件作者写对了 peer 范围也没用，用户装的时候既看不到告警、又拦不住。** 这解释了为什么大家普遍抱怨"升级后突然发现一堆插件是坏的"。

## 机制五（附加）：会话持久化格式在变，且历史上有"变了不升版本"

`docs/persistence-changes/releases/` 是官方逐 tag 归档的格式变更记录：**26 个 tag、25 次相邻转换**。

| Tag | 日期 | Session 版本 | 变化根 |
|---|---|---|---|
| dsh-v0.1.2-alpha.1 | 2026-08-27 | 0 | **52** |
| dsh-v0.1.2-alpha.2 | 2026-08-30 | 0 | **52** |
| dsh-v0.1.3-alpha.1 | 2026-09-04 | **2** | 17 |
| dsh-v0.1.5-alpha.1 | 2026-09-08 | **3** | 12 |

关键两点，官方文档原文：

1. > 这些回溯记录与上层目录的当前确认链分开校验。当前规则对旧变化的分类只是阅读提示：**历史上的 version 0 确实出现过不升版本的结构变化。**

   即：**格式变了，版本号没变** —— 靠版本号判断兼容性会踩空。

2. > 前 22 个 tag 的 surface 事件合法地带有可选 `surfaceOp`。历史解析保留此可选性；**当前源码解析仍要求该字段必需。**

   即：字段从**可选变必需**——旧插件产出的数据直接被判非法。

仓库里还挂着 `migrate:sessions-to-v4` 脚本，说明当前正在往 Session v4 迁移。

**任何读写 session 的插件（记忆、导出、回放、UI 时间线）都会被静默打穿**，而且症状常常不是报错，是"数据没了/显示不对"。

## 对"我要做一个插件"的实际意义

这些坑反过来就是护栏清单：

| 护栏 | 做法 | 踩了会怎样 |
|---|---|---|
| 用命名导出 | `export const name / export const inject / export function apply`，**绝不加 `export default`** | Loader 丢弃 inject，加载瞬间崩 |
| 显式声明 inject | 用到哪个服务就在 `inject` 数组里写全 | 抛 `cannot get property "X" without inject` |
| 可选服务用 `ctx.get()` | 机会性读取的服务写 `ctx.get('name')`，**不要写 `ctx.name`** | 属性代理只向祖先 fiber 遍历，兄弟分支读不到直接抛错 |
| 锁精确版本 | 依赖官方包写精确版本，不用 `^` | pnpm 静默拉到不兼容版本，且无告警 |
| 加载测试不可省 | 每次官方发版，用**真实 Loader** 端到端跑一次 | 官方 Postmortem 0001：**178 个单元测试全绿、100% 行覆盖率，生产环境照样全崩** |
| 优先扩展点，别改内核 | 用 `ctx.tools.register()` 等公开扩展点 | 改内核 = 每次发版都要手工适配 |

关于最后一条，官方扩展手册的表述是：`No row modifies the loop`（没有任何产品功能需要改动主循环）——**默认不需要 fork**。
