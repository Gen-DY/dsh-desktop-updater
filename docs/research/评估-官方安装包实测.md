# 官方桌面端安装包实测 —— 对双模式更新方案的影响

**日期**：2026-09-28
**触发**：网上有人称官方 Windows 桌面端产物已出现在生产下载源（未官宣）

---

## 一、结论先行

**官方确实有 Windows 安装包，而且我们之前的三条核心假设有两条被推翻了。**

| 之前的判断（2026-09-21 记录） | 现在实测 |
|---|---|
| 官方 production feed 实测 404（未公开） | ❌ **已过时** —— `win-x64/nightly.yml` 现在 **HTTP 200** |
| 本地构建的包不具备自动更新能力 | ✅ 仍成立（针对我们自己的 unsigned 包） |
| 需要自建 feed 托管才能"检查更新" | ⚠️ **不再必要** —— 官方包**自带**更新配置 |

### 2.4 ⭐ 数字签名：**EV 代码签名**

解析 PE 证书表（13,288 字节）：

| 项 | 值 |
|---|---|
| 签名主体 | **`Hangzhou DeepSeek Artificial Intelligence Co., Ltd.`** |
| 证书链 | **`GlobalSign GCC R45 EV CodeSigning CA 2020`** |
| 时间戳 | `DigiCert SHA256 RSA4096 Timestamp Responder 2026`（长期有效） |

**EV 代码签名意味着安装时不会弹 SmartScreen 警告** —— 而我们的 unsigned 包会弹。

### 2.5 ⭐⭐ 官方包内置 `resources/app-update.yml`

用 7za 解包官方 exe 得到（306 字节）：

```yaml
provider: generic
url: https://download.deepseek.com/dsh-desk/feeds/win-x64/
channel: nightly
updaterCacheDirName: '@deepseek-aidsh-desktop-updater'
publisherName:
  - CN=Hangzhou DeepSeek Artificial Intelligence Co., Ltd.,O=Hangzhou DeepSeek Artificial Intelligence Co., Ltd.,C=CN
```

**这是本次最重要的发现**：官方包**自带完整的自动更新配置**，指向官方 CDN。

## 三、`publisherName` 的含义（关键约束）

`electron-updater@6.8.9` 里，`NsisUpdater` 在安装前会调用：

```js
// NsisUpdater.js
this._verifyUpdateCodeSignature = (publisherNames, unescapedTempUpdateFile) =>
  verifySignature(publisherNames, unescapedTempUpdateFile, this._logger)
```

`windowsExecutableCodeSignatureVerifier.js` 用 PowerShell 的
`Get-AuthenticodeSignature` 校验签名主体是否匹配。

**推论**：

| 从 / 到 | 能否更新 |
|---|---|
| **官方签名包 → 官方 feed** | ✅ 正常（签名主体匹配） |
| **官方签名包 → 我们的 unsigned 包** | ❌ **会被拒绝**（主体不匹配） |
| **我们的 unsigned 包 → 官方签名包** | ✅ 应可（我们的 `app-update.yml` **没有** `publisherName`，不校验签名） |

> 最后一行待实测确认，但方向明确：**单向兼容**。

## 四、对我们方案的影响

### 4.1 方式一（自建 feed 分发）→ 基本可以退役

官方包已经自带"feed + 签名 + 差分"，而且：
- 包是**签名的**（我们的不是）
- CDN 速度 **17.7 MB/s**（我们走 GitHub，之前实测 9.16 MB/s）
- **用户装官方包后，什么额外东西都不用装就有更新能力**

我们自建这条路的**唯一剩余价值**是：官方 CDN 不可达时的兜底（内网/受限网络）。

### 4.2 方式二（本地构建）→ 保留，但定位变了

用途从"提供更新渠道"变成：
- **想改代码 / 定制**（官方包改不了）
- **内网部署**（CDN 不可达）
- **固定版本**（官方 feed 一直在动）
- **构建受审计的版本**

我们工具里价值最实的三块反而在方式二周边：
**环境预检**（13 项）、**构建补丁托管**（幂等 + fail loudly）、**兼容性校验**。

### 4.3 我们已构建的 rc.1 包

**落后于官方的 rc.2**，且未签名。**没有分发价值了**（除非做兜底）。

## 五、建议

1. **立刻可用**：官方 rc.2 安装包已验证完整（sha512 一致、EV 签名），
   已下载到 `C:\Users\a1207\AppData\Local\Temp\dsh-rc1\official-rc2.exe`，双击即可装。

2. **方案调整**：
   - 方式一 → 降级为"官方 CDN 不可达时的兜底"，或直接删掉
   - 方式二 → 保留为**本地构建工具**
   - 文档与 UI 的"信息结构"要跟着改（官方版本区块仍有用，但"我的仓库版本"可弱化）

3. **验证更新链路的最快办法**（不用重新构建）：
   装我们的 unsigned rc.1 → 把它的 `resources/app-update.yml`
   的 `url` 改成 `https://download.deepseek.com/dsh-desk/feeds/win-x64/`
   → 点「检查更新」应发现 **0.1.7-rc.2** → 下载 → 安装 → 重启。
   这同时验证了"unsigned 包能否升级到官方签名包"这条推论。

4. **待观察**：这是 `nightly` 通道、官方**未官宣**（官网无下载入口、GitHub Release 无资产、
   `latest.yml` 仍 404）。URL 结构可能变，不宜把产品逻辑硬绑到它上面。
