# 可行性评估：把「源码升级 → 打包 → 安装」做进「检查更新」

> 评估日期：2026-09-23
> 源码基准：`D:\codes\deepseek-harness` @ `0.1.7-alpha.2`
> 结论一句话：**可行，而且比预想的容易——官方已经实现了整条链路的后半段，"直接更新安装版"这件事不用自己写。真正的卡点在"前端驱动"这一环，那是官方的刻意设计。**

---

## 一、先定位你现在的痛点

你那个包点「检查更新」永远失败，根因在源码里写得很清楚。

`apps/desktop/scripts/electron-builder-config.mjs:92`：

```js
const update = unsigned ? undefined : resolveDesktopAutoUpdateConfig(env, resolvedPlatform, resolvedArch)
```

同文件 `:240`：

```js
publish: update === undefined ? null : [{ provider: 'generic', url: update.publicUrl, channel: 'nightly' }],
```

链路是这样断的：

| 步骤 | 事实 |
|---|---|
| 你打了 `DSH_DESKTOP_UNSIGNED=1` | `unsigned === true` |
| 于是 `update = undefined` | — |
| 于是 `publish: null` | electron-builder **不生成** `app-update.yml`，也**不生成** `nightly.yml` |
| 而运行时 `src/update-coordinator.ts:53` | `enabled()` 要求 `app.isPackaged && existsSync(resources/app-update.yml)` |
| 结果 | `doCheck()` 抛 `desktop update: this application has no packaged update source` |

**注意**：`publish` 只影响 feed 与 `app-update.yml` 的生成，**不影响 `forceCodeSigning`**（那是 `win.forceCodeSigning: !unsigned`，`:216`）。所以给 unsigned 构建补一个 `publish` 配置，**不需要证书**。

---

## 二、官方已经实现的部分（白拿）

### 2.1 完整的下载安装编排 —— 这是最有价值的一条

`src/update-coordinator.ts` 就是一台现成的状态机：

| 方法 | 行为 | 源码 |
|---|---|---|
| `check()` | 读 feed 元数据，比对版本 | `:178-191`，`checkForUpdates()` + `semver.gt` |
| `download(version)` | 下载 + 进度 + 校验 | `:99-118`，`downloadUpdate()` |
| `install(version)` | **停止任务 → 退出 → 装 → 重启** | `:125-141` |

`install()` 的关键三行：

```ts
if (!await this.beforeRestart()) return this.setState({ phase: 'ready', version })
this.updater.quitAndInstall(true, true)   // (isSilent, isForceRunAfter)
```

`beforeRestart` 由主进程注入，负责**任务授权、admission 锁、owned 进程退出**——也就是"先把正在跑的任务停干净再换程序"。**这套编排官方写好了，不用你碰。**

### 2.2 feed 格式是标准的 generic provider

`scripts/installed-update-builder.ts:37`（官方自己构建安装版更新时的配置）：

```ts
publish: [{ provider: 'generic' as const, url: `${run.origin}/${run.feedKey.slice(0, -'nightly.yml'.length)}`, channel: 'nightly' }],
```

`scripts/desktop-auto-update-environment.mjs:80`：

```js
return `nightly${platform === 'darwin' ? '-mac' : ''}.yml`
```

→ **feed 就是一个静态的 `nightly.yml` + 一个 exe**。这跟你已有的 GitHub Release 产物形态几乎一样。

### 2.3 官方甚至给了可用性测试夹具

`tests/fixtures/local-updater.mjs`（386 行）用 `NsisUpdater` + 本地 server 完整演练了：feed 404 / 超时 / 校验失败 / ENOSPC / 并发检查去重 / 陈旧版本拒绝 / 安装前确认。**可以直接拿它当验收清单**。

## 三、三条路线

### 路线 A｜只补 feed（推荐先做）

**动作**：
1. 让 unsigned 构建也带上 `publish: [{ provider:'generic', url:'<你的托管地址>/', channel:'nightly' }]`
2. 构建产物里就会多出 `nightly.yml`，把它和 exe 一起发布
3. 装完的包里会多一个 `resources/app-update.yml`

**得到**：手动跑一次构建 → 点「检查更新」→ 自动下载 → 确认 → `quitAndInstall` 静默安装并重启。**"直接更新安装版"这一条完整达成。**

**代价**：改 1 处配置 + 准备一个静态托管位置。

**注意**：官方 `resolveDesktopAutoUpdateConfig` 的 `httpsOrigin()`（`:111-118`）**强制 HTTPS 裸 origin**（不能带路径/凭证/query/fragment）。所以
- ❌ `http://127.0.0.1:8080/` 套不进去
- ✅ 真实 HTTPS 托管（你的 GitHub Release、自建域名、对象存储）
- ⚠️ 若坚持本地 HTTP，得**绕开这个函数**自己给 `publish` 配 url——electron-builder 本身不强制 HTTPS

### 路线 B｜UI 插件 + 宿主侧构建

**关键发现**：web 前端的更新 UI 在 `packages/client/ui-settings-general`，而它**本身就是一个标准 Cordis 客户端插件**：

```ts
export const inject = ['slots', 'locale', 'connection', 'remote', 'remote.settings', 'configForms']
export function apply(ctx: ClientContext): void {
  ctx.slots.inject('settings.general.item', () => ctx.slots.register({
    name: 'settings.general.item', id: 'current-version', order: 100, locale: NS,
  }, CurrentVersionRow))
  ...
}
```

所以**界面层可以做成独立插件**，往 `settings.general.item` 或 `settings.section` 注册自己的行/节。这一层不用改内核。

**但**：它与主进程之间只有一条受限的桥（`packages/client/ui-settings-general/src/types.ts:24`）：

```ts
/** Optional carrier API; it cannot select artifacts or authorize installation. */
export interface DesktopUpdateBridge {
  status(): Promise<DesktopUpdatePresentation>
  open(): Promise<void>
  subscribe(listener: (state: DesktopUpdatePresentation) => void): () => void
}
```

宿主侧构建（spawn 你的 `prepare-build.cjs`）插件自己能做，但**"安装"这一步过不去**——插件没权限授权安装，只能调 `open()` 让主进程弹确认框。

### 路线 C｜改桌面端内核

**动作**：改 `src/ipc.ts`（加 IPC 通道 + 扩桥）、`src/preload-*.ts`、`src/main.ts`、`src/update-coordinator.ts`（加 `building` 阶段）、`renderer/update-dialog.*`（加进度 UI）。

**得到**：完整"一键构建 + 更新"。

**代价**：
- 改 4~6 个内核文件
- **永久跟随上游**——正是上一轮调研里说的 fork 债务，这次会真实撞上
- 且 `apps/desktop` 是内核，不是插件，改动没法用插件机制隔离

## 四、四条硬约束（动手前必须知道）

| # | 约束 | 说明 |
|---|---|---|
| 1 | **Windows 文件锁** | 正在运行的 exe 无法自我覆盖。必须走 `quitAndInstall` → 主进程退出 → NSIS 替换 → 重启。官方已实现，**别自己写替换逻辑** |
| 2 | **前端被架构禁止授权安装** | `src/ipc.ts:61` 原文：*"Product documents cannot supply update versions, package URLs, or installation authorization."* 这是安全设计，不是遗漏 |
| 3 | **构建环境是硬依赖** | 装更新那台机器必须有：完整源码工作区 + pnpm store + VS + Windows SDK。同机自用可行，换台机器就不成立 |
| 4 | **`quitAndInstall` 会重启应用** | 构建进度 UI 会随重启丢失；构建与安装必须分两段，中间落盘 |

补充：unsigned 包生成的 `app-update.yml` 不含 `publisherName` → electron-updater **不验代码签名**，只校验 `sha512`。所以 unsigned 自更新链路能跑通。

---

## 五、建议

**先做路线 A。** 理由：

1. 投入极小（1 处配置 + 一个托管位置），收益极大——你那个包现在「检查更新」是**死的**，A 能让它活过来
2. A 跑通后，"更新安装版程序"这个最难、最容易出事的部分（文件锁、进程退出、安装器编排）就已经**验证过了**，而且是官方代码在扛
3. 之后再决定构建编排放哪：放插件里（B，不脏内核）还是放「检查更新」里（C，脏内核）

一句话：**A 是必做项，B 和 C 是可选项。**
