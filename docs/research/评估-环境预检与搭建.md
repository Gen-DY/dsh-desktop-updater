# 可行性评估（第二轮）：环境预检 + 一键搭建环境

> 评估日期：2026-09-23
> 前置文档：`检查更新接入本地构建-可行性评估.md`（第一轮：feed 与安装链路）
> 新增需求：检查更新时**同时检查本机构建环境**（源码工作区、依赖、磁盘空间…），不满足时**提供"帮你搭建环境"的选项**

---

## 结论（三句话）

1. **环境预检：完全可行，而且价值已被实测证实。** 原型脚本已跑通，本机判定 **通过 10 / 警告 2 / 阻断 1**——唯一阻断项是磁盘空间。这证明预检不是摆设，它真的会抓到东西。
2. **一键搭建环境：必须拆成三类。** 工具链（Node/pnpm/源码/依赖）可以真自动；磁盘空间只能引导；**Visual Studio + Windows SDK 基本上做不到自动**——需要管理员权限 + 数十 GB + 20~40 分钟。
3. **但更关键的是一个方向性问题**：如果目标用户是同事，那么"让同事机器具备构建能力"这条路**经济性极差**。正确做法是**构建端与安装端分离**——详见第五节。

---

## 一、环境预检：可行，且有官方范式

### 1.1 官方已经给你打了个样

`apps/desktop/scripts/desktop-toolchain-preflight.ts` 就是官方的构建环境预检，它的设计理念原文：

> *Each probe here exercises the specific behaviour the run depends on rather than merely checking that the executable resolves.*
> （每个探针都实跑它依赖的真实行为，而不是只检查可执行文件能不能解析到。）

它只查两项：

| 探针 | 做法 | 为什么这么做 |
|---|---|---|
| `tar` | **真的打一个包再解一次** | GNU tar 会把绝对路径里的 `D:` 当远程主机——只看命令存在完全抓不到这个坑 |
| `vswhere` + `VC.Tools.x86.x64` | 用 VS 官方定位器查组件 | 原生安装器 UI 必须 MSVC 编译 |

**骨架可以照搬，扩展成完整清单即可。**

### 1.2 我按这个范式扩展成 12 项，并跑了实测

原型：`preflight-build-env.cjs`（纯 Node，无依赖，可被 .bat 或前端调用）。

**本机实测结果**：

| | 项 | 实测 | 判定 |
|---|---|---|---|
| ✗ | **磁盘空间** | **D: 仅剩 13.7 GB（构建需 ≥15 GB）** | **阻断** |
| ! | Windows SDK | 最高 10.0.19041.0（需 GDI+ 补丁） | 警告 |
| ! | 管理员权限 | 普通用户 | 警告 |
| ✓ | Node.js | v22.22.2 | 通过 |
| ✓ | pnpm | 11.7.0（正好是仓库钉的版本） | 通过 |
| ✓ | git | 2.53.0 + 仓库带 `.git` | 通过 |
| ✓ | VS C++ 工具链 | 2019 Community 16.11.53 | 通过 |
| ✓ | 源码工作区 | `0.1.7-alpha.2` | 通过 |
| ✓ | node_modules | 42 项 | 通过 |
| ✓ | `.env.windows` | 存在 | 通过 |
| ✓ | pnpm store | `D:\.pnpm-store` | 通过 |
| ✓ | 代理 | `127.0.0.1:17890` 可连 | 通过 |
| ✓ | tar | 可正常打包解包 | 通过 |

**注意第一行：你这台机器现在就跑不了完整构建。** D 盘只剩 13.7 GB，一次构建要重建 node_modules + electron + 内嵌 runtime（node/pnpm/python/libreoffice）+ win-unpacked + 安装包 + zip。这就是"预检"最直接的价值——**避免白跑 30~60 分钟**。

### 1.3 实测踩到的两个实现坑（已修）

| 坑 | 现象 | 修法 |
|---|---|---|
| `pnpm`/`npm` 是 `.cmd` 包装 | `execFileSync('pnpm')` 报「未找到」，但命令行明明有 | 过 shell 调用 |
| `vswhere` 路径含空格与括号 | 过 shell 反而被引号吃掉 | **不过** shell，用绝对路径直调 |

同一份脚本里两类调用必须分开处理——这个坑不踩一次想不到。

## 二、一键搭建环境：分三类，别指望全自动

| 类别 | 具体项 | 能否自动化 | 说明 |
|---|---|---|---|
| **可全自动** | Node/pnpm 版本修正 | ✅ | 静默安装即可 |
| | 拉取源码工作区 | ✅ | git clone 或 tarball 铺设（走代理） |
| | `pnpm install` | ✅ | 耗时但无人值守 |
| | 生成 `.env.windows` | ✅ | `prepare-build.cjs` 第 5 步已实现 |
| | 代理/镜像环境变量 | ✅ | 写进构建脚本即可 |
| | pnpm store 预热 | ✅ | 可选加速 |
| **只能引导** | **磁盘空间** | ⚠️ | 能检测、能算出需要多少、能列出清理目标，**但不能替用户删**。而且受限环境下"删到回收站"并不释放空间，必须清空回收站——这一步无法代劳 |
| **基本做不到** | **Visual Studio + Windows SDK** | ❌ | 见下 |

### 为什么 VS + SDK 不能自动装

| 障碍 | 事实 |
|---|---|
| **权限** | 安装必须管理员提权。实测本机 `IsUserAnAdmin() == False`（普通用户） |
| **体积** | VS C++ 工作负载 + SDK ≈ 10~15 GB 下载、20~30 GB 占用 |
| **时长** | 20~40 分钟，可能要求重启 |
| **企业环境** | 码头这类环境下，普通员工常没有本机管理员权限，IT 也未必允许自装开发工具链 |

**所以对 VS/SDK 的正确形态是「引导式安装」**：预检给出精确的缺失项 → 给出官方下载地址与需要勾选的组件名（`Microsoft.VisualStudio.Component.VC.Tools.x86.x64` + Windows 10/11 SDK）→ 用户装完 → **重新预检**。

这不是妥协，是这类依赖的行业通行做法——**检测全部可自动，安装留给用户确认**，因为安装本身是不可逆的重操作。

## 三、但这里有个方向性错位，需要先拍板

你把"环境预检"挂在「检查更新」上，但这两件事的服务对象其实不是同一台机器：

| | 装在哪台机器 | 需要什么 |
|---|---|---|
| **「检查更新」** | 每个用户的机器 | 只要网络 + 磁盘空间 |
| **构建能力** | **只有构建机** | 源码 + VS + SDK + pnpm + 20 GB 空间 + 管理员权限 |

**用户机器上的「检查更新」去检查"有没有源码工作区、有没有 VS"——检出来的问题用户既解决不了（没权限），也不需要解决（他不需要构建）。**

所以正确切分是：

- **用户端**：检查更新 = 查版本 → 下载 → 安装。（官方 `update-coordinator.ts` 已完整实现，见第一轮评估）
- **构建机端**：环境预检 + 引导搭建 = 独立入口。放哪儿？`packages/client/ui-settings-general` 里已经有个现成的 **`DeveloperToolsRow`**（开发者工具开关），那类位置才合适。

## 四、如果目标是给同事用——建议换方向

你问"是否要帮他搭建这样的环境"，我理解目标是让同事也能用上更新。那先把账算清楚：

**方案甲：每台机器都能构建（你原本的设想）**

| 同事机器需要 | 代价 |
|---|---|
| 源码工作区 | ~2 GB + 拉取时间 |
| Visual Studio C++ | 10~15 GB + **管理员权限** |
| Windows SDK | ~3 GB |
| pnpm store + node_modules | 5~10 GB |
| 磁盘余量 | 20 GB+ |
| 每台机器首次搭建 | 1~2 小时 |

**方案乙：构建端与安装端分离（推荐）**

| | 谁做 | 需要什么 |
|---|---|---|
| 构建 + 出包 + 发 feed | **只有你** | 你现有的环境 |
| 下载 + 安装 | 每个同事 | 网络 + ~2 GB 磁盘 |

**方案乙里，同事端零构建依赖**——不需要源码、不需要 VS、不需要 pnpm、也不需要管理员权限（`electron-builder-config.mjs:233` 是 `perMachine: false`，装到用户目录）。

而且这正好就是第一轮评估的**路线 A**：喂一个 feed 进去，官方整套下载安装链路就跑起来了。你已经有 GitHub Release 的流程，feed 托管这一环几乎是现成的。

**结论：如果目标是"让同事也能更新到你的构建版"，方案乙是唯一合理的选择。**"环境预检 + 自动搭建"只在**你自己的构建机**上有价值（换机器、重装系统时重建环境）。

---

## 五、建议的实施顺序

1. **先做预检，且只做预检**（本次已出原型）
   纯 Node 脚本，无依赖，先解决"白跑 30~60 分钟"这个最痛的点。实测已证明它抓得到问题（本机磁盘就是不达标）。
2. **把预检挂到构建机入口**，不要挂「检查更新」
   现有 `.bat` 的第 1 步就是它的位置；将来若做前端面板，放 `DeveloperToolsRow` 那一类开发者区域。
3. **引导式修复，别做自动安装**
   给出精确的缺失项 + 官方下载地址 + 需勾选的组件名，装完重新预检。VS/SDK 的自动安装不做。
4. **同事端走"构建/安装分离"**
   你构建 → 发 feed → 同事只下载安装。这才是"给同事用"的正解。
