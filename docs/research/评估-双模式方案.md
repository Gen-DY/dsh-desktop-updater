# 可行性评估（第三轮）：双模式并存

> 评估日期：2026-09-23
> 前置文档：`检查更新接入本地构建-可行性评估.md`（feed 与安装链路）、`环境预检与自动搭建-可行性评估.md`（预检与三类搭建）
> 新增需求：**同时提供两种更新方式，由用户选择**——① 分离式（你构建丢 GitHub，用户拿来用）；② 本地构建式。环境搭建按三类处理（可自动的自动、磁盘空间只告警、VS/SDK 只检测推荐）

---

## 结论

**可行，而且双模式比单模式更合理——因为两种模式共用的部分最大，差异只有一处。**

一句话概括架构：

```
环境预检 → 构建 → feed  →  检查更新 → 下载 → 安装重启
└──── 只有模式②才有 ────┘  └──── 两种模式完全共用 ────┘
```

**右半段（检查更新 → 下载 → 安装重启）两种模式一模一样**，都是 electron-updater 消费一个 generic feed。差异只在 **feed 从哪来**：

| | feed 来源 | 谁构建 |
|---|---|---|
| **模式①分离式** | GitHub Release（远程 HTTPS） | 你 |
| **模式②本地构建** | 本机临时 HTTP 服务（127.0.0.1） | 用户本机 |

**环境预检只属于模式②**，挂在模式②的入口上即可，不影响模式①。

---

## 一、模式①（分离式）的验证

### 1.1 好消息：GitHub 是一等公民

`electron-updater@6.8.9` 自带四类 provider：`Generic`、`GitHub`、`PrivateGitHub`、`GitLab`/`Bitbucket`/`Keygen`。

**GitHub Release 不需要你自己攒 feed** —— 直接把 release 资产当 feed 用，官方 provider 会处理 channel 解析。

### 1.2 ⚠️ 必须解决的障碍：你的仓库是私有的

`Gen-DY/deepseek-harness-desktop-build` 是**私有仓库**。私有仓库的 Release 资产下载**需要凭据**，同事没有 GitHub token 就下不到。

三个解法：

| 方案 | 做法 | 评价 |
|---|---|---|
| **单开公开产物仓库** ⭐ | 新建一个**公开**仓库，只放 `exe` / `zip` / `nightly.yml`；构建脚本继续留在私有仓库 | 最干净。产物本来就没什么可保密的，构建工具链才需要私密 |
| Generic + 其他 HTTPS 托管 | 内网静态服务器 / 对象存储 / Gitee 附件 | 码头内网可能比 GitHub 更稳，值得考虑 |
| 私有仓库 + 分发 token | `app-update.yml` 带 `requestHeaders` | ❌ 不推荐：token 打进安装包等于公开 |

另外注意：你是**从受限网络走代理**推 GitHub 的，但同事的网络环境未必一样。**如果同事访问 GitHub 不稳定，内网静态服务器反而是更实际的选择。**

## 二、模式②（本地构建）的验证

### 2.1 ✅ 本机 HTTP feed 可行（关键结论）

之前担心官方 `httpsOrigin()` 强制 HTTPS 会把本地服务挡掉。查证结果：

| 环节 | 事实 | 结论 |
|---|---|---|
| `GenericProvider` 构造 | `this.baseUrl = newBaseUrl(this.configuration.url)` | — |
| `newBaseUrl` 实现 | `const result = new URL(url)`，**不校验协议** | ✅ http 可用 |
| 官方的 `httpsOrigin()` | 位于**打包脚本** `desktop-auto-update-environment.mjs` | 只是打包时校验，**不是运行时限制** |
| `DesktopUpdateHttpExecutor` | 继承 `ElectronHttpExecutor`，基于 Electron net | ✅ http 可用，❌ **file:// 不可用** |

**结论：`http://127.0.0.1:<port>/` 作为 feed base URL 完全可行**，只要绕开官方打包脚本那个校验、自己写 `app-update.yml`。

**但 `file://` 不行**——Electron 的 net 模块不处理 file 协议。所以模式②需要**起一个本地 HTTP 服务**。

实现成本很低：Node 内置 `http` 模块，托管一个目录（`nightly.yml` + exe），构建完起、更新完关，十几行代码。下载环节实质是从 127.0.0.1 复制一遍产物（几百 MB，几秒）。

### 2.2 三种路径对比

| 路径 | 能否复用官方 `quitAndInstall` 编排 | 说明 |
|---|---|---|
| 本机 HTTP feed ⭐ | ✅ 完全复用 | 推荐 |
| `file://` 直接读 | ❌ 不可行 | Electron net 不支持 |
| 构建完直接 `shell.openPath(安装器)` | ❌ 丢掉编排 | 简单，但**丢掉了"停任务→退出→装→重启"**——而这是 Windows 文件锁下唯一可行的安装方式，不能丢 |

| 类别 | 落地形态 |

| **可自动** | 一键执行 + 进度反馈：Node/pnpm 版本修正、拉源码、`pnpm install`、生成 `.env.windows`、代理变量、store 预热 |

## 四、两个架构建议（否则会埋坑）

### 4.1 显式分流，不要自动判断

两种模式塞进同一个"检查更新"按钮里自动决策，会出现这些麻烦：
- 用户不知道自己会被怎么更新
- 模式②的预检结果变成"隐藏的降级逻辑"，出问题难排查
- 语义混乱：「检查更新」到底是查版本还是查环境？

**建议**：进入更新面板先选来源。

```
更新面板
 ├─ 从共享源更新   （模式①，默认，所有人可用）
 └─ 本地构建更新   （模式②，先跑环境预检，通过才允许构建）
```

### 4.2 构建与安装必须分两段

`quitAndInstall` **会重启应用**，而一次构建要 30~60 分钟。如果合成一个动作，用户就得盯一个不能关的窗口一小时。而且这台机器现在磁盘还不达标，构建随时可能失败。

**建议分成两段**：

| 段 | 是否阻塞 | 失败后 |
|---|---|---|
| 构建 | 可后台跑，用户能做别的（甚至可以先干别的活） | 可重跑（构建本身幂等，`prepare-build.cjs` 就是按幂等写的） |
| 安装 | 才走 `quitAndInstall`（停任务 → 退出 → 装 → 重启） | 官方编排有回退文案 |
