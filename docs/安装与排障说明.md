## 2. .bat 的五步流程

双击 `install-deepseek-desktop.bat` 后，它在 cmd 窗口里依次执行：

| 步骤 | 做什么 | 大致耗时 |
|---|---|---|
| `[1/5]` | 环境检查 —— `node -v` / `pnpm -v`，缺则直接报错退出 | 秒级 |
| `[2/5]` | 构建前准备 —— 调用 `prepare-build.cjs`，共 **6 项本地修补**（SDK 补丁 / 清陈旧编译残留 / 清孤儿包目录 / 清坏链接 / 纠正更新通道 / 壳页面协议分支） | 秒级 |
| `[3/5]` | `pnpm install --force` —— 重建 `node_modules` | 首次 10–30 分钟 |
| `[4/5]` | `pnpm run package:desktop:win:x64:unsigned` —— 打包未签名安装包 | 20–40 分钟 |
| `[5/5]` | 列出产物并**自动启动安装程序** | — |

### 只想「重出一次包」时可以只跑第 4 步

依赖没变、只是想重新打包（例如改了 `.env.windows`）时，可以跳过 1–3 步，直接在仓库根跑：

```bat
node prepare-build.cjs
pnpm run package:desktop:win:x64:unsigned
```

- **第 4 步就是 `.bat` 的核心** —— `.bat` 只是它外面套了环境检查、前置修复、装依赖和收尾启动。
- ⚠️ **但别漏掉 `node prepare-build.cjs`**（1 秒）：它负责 SDK 补丁、清陈旧编译残留、清坏链接、
  **纠正 `.env.windows` 的更新通道**，以及**校验**上游的壳页面协议分支是否还在。
  少了它，那些老坑（`MISSING_EXPORT`、SDK 编译失败）会回来。
- 直接跑第 4 步**不需要** `.bat` 里那些环境变量：`prepare-dsh` 自己写死了
  `--config.registry=https://registry.npmjs.org/`，还会主动剥掉继承来的 `npm_*`/`pnpm_*` 变量；
  两个镜像只在首次下载 Electron/NSIS 时会用到，而 `.desktop-build\downloads` 已有缓存。
- 跑完**不会自动启动安装程序**，需要自己双击产出的 exe。

| 场景 | 用哪个 |
|---|---|
| 首次装 / 换机器 / `git pull` 拉了新代码 / `node_modules` 坏了 | **双击 `.bat`**（它会帮你把坑都填了） |
| 只改了打包配置、想快速重出一次包 | `node prepare-build.cjs` + `pnpm run package:desktop:win:x64:unsigned` |

脚本里已经固化了所有必要参数，**不需要手动改任何配置**：

```
npm_config_registry=https://registry.npmjs.org          # 官方源（npmmirror 在这台机器上会报 error 23）
npm_config_trust_lockfile=true                          # 跳过 pnpm 11 的 lockfile 供应链复验
npm_config_confirm_modules_purge=false                  # 避免无 TTY 时死等"是否清理 node_modules"确认
ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/
ELECTRON_BUILDER_BINARIES_MIRROR=https://npmmirror.com/mirrors/electron-builder-binaries/
PYTHON=D:\Program Files\Python313\python.exe            # 存在才设
DSH_CLIENT_COMMIT_HASH=...                              # 仅在缺 git / 缺 .git 时自动填占位值（见 §11）
```

> 两个镜像已实测可用（`winCodeSign-2.6.0.7z`、`electron-v44.0.0-win32-x64.zip` 均返回 206）。
>
> `DSH_CLIENT_COMMIT_HASH` 是构建系统预留的开关：正常有 `.git` 时不设它，写真实 commit；检测不到就填 40 个 0 兜底，
> 只影响构建信息里显示的版本号，不影响功能。

## 3. 本地修补，以及同步官方代码后的行为

仓库上游 CI 用的 SDK 比本机新，所以本机直接构建会失败。修补全部封装在 `prepare-build.cjs` 里（**幂等**，可重复运行，已打过则跳过），`.bat` 每次都会调用它。

### 3.1 Windows SDK 10.0.19041.0 兼容补丁

**现象**：`build:lib` 阶段报 `Native installer helper compilation failed`，但编译器输出被脚本吞掉了。真实错误在证据日志里：

```
GdiplusTypes.h(479): error C3861: "min": 找不到标识符        ×16
GdiplusHeaders.h(701): warning C4458: ... 隐藏了类成员        ×7
```

**根因**：**23 条诊断全部来自 SDK 自带头文件，没有一条来自仓库代码。**

- 本机 VS2019 Community 16.11 只能配到 SDK `10.0.19041.0`
- `window-frame.cpp` 定义了 `NOMINMAX` 关掉 min/max 宏，而该 SDK 的 `GdiplusTypes.h` 用的是**裸 `min`/`max`** → 16 个 C3861
- 该 SDK 的 GDI+ 头文件自带 C4458，而构建脚本用 `/W4 /WX`（**警告即错误**）→ 7 个变错误
- 新版 SDK 这两处都已修掉，所以上游 CI 不受影响

**补丁内容**（写在 `#include <gdiplus.h>` 之前）：

```cpp
#include <dwmapi.h>
#include <algorithm>
using std::min;
using std::max;
#pragma warning(push)
#pragma warning(disable: 4458)
#include <gdiplus.h>
#pragma warning(pop)
```

**验证结果**：`window-frame.dll`(98KB) + `.lib`/`.exp`/`.obj` + 5 个 BMP 全部产出，编译日志 **0 error / 0 warning**。

### 3.2 陈旧编译残留清理

**现象**：`build:tsdown` 报 `MISSING_EXPORT`，说 `assertNever` / `snapshotJsonValue` 没有导出——**看着像源码缺导出，其实是假象**：

| 对照 | 内容 |
|---|---|
| 报错的文件 | `packages/workflow/workflow-worker-thread/lib/types/host.js` → 从 `dsh-llm` 导入 |
| master 的正确源码 | `packages/workflow/workflow-ptc/src/host.ts` → 从 `dsh-util-values` 导入 |
| 关键点 | `@deepseek-ai/dsh-workflow-worker-thread` **这个包 master 里已经删了** |

**根因**：跨版本升级（rc.7 → 0.1.6-alpha.2）时，旧包被删掉，但 `.gitignore` 忽略的 `lib/` 和 `node_modules/` 还留在磁盘上，形成**"孤儿包目录"**（只剩 `lib`/`node_modules`、没有 `package.json`）。里面的旧 JS 导入关系早已过时。这类目录 **`git clean -fd` 清不掉**（被 gitignore 保护），共 **16 个、723 个文件**。

**清理三件事**：
1. 删除根目录陈旧的 `*.tsbuildinfo`（否则 `tsc -b` 增量状态会骗过重建，`lib/` 不重新生成）
2. 删除 `packages/*/*` 下没有 `package.json` 的孤儿包目录
3. 保底：遇到含未知文件的残留会**跳过不删**（fail-safe，与仓库自带 `scripts/clean.ts` 策略一致）

**验证结果**：`MISSING_EXPORT` 从 2 个 → **0 个**，构建推进到第 247+ 个打包目标。

### 3.3 `dsh-app://shell/*` 协议分支（**上游已修复，本地补丁已退役**）

**现象**：点「检查更新」→ 整个界面发白模糊、点不动、任务栏也关不掉，只能杀进程。详见 **§14**。

**根因**：`apps/desktop/src/main.ts` 的 `protocol.handle` 只处理 `url.hostname === 'app'`，其余一律返回 `404 + 空 body`。而三种对话框都从 `dsh-app://shell/` 加载页面，于是页面全白，只剩一层透明 modal 盖着父窗口。

**现状**：✅ 上游 **0.1.7-alpha.2 起已自行修复**，代码与本地当年写的补丁**逐字一致**：

```ts
// apps/desktop/src/main.ts  (protocol.handle 内)
if (url.hostname === 'shell') return serveWebDocument(request, join(app.getAppPath(), 'renderer'))
```

所以本地**不再需要**这个补丁。`prepare-build.cjs` 第 6 步已从「打补丁」改成「**校验 + 兜底**」：

| 情况 | 行为 |
|---|---|
| 上游自带 shell 分支（当前状态） | 打印「无需本地补丁 ✓」并跳过 |
| 上游哪天回退了该分支 | 自动补回那 7 行，并警告可能重现「发白卡死」 |
| 代码结构改写，两边都判断不出 | `exit 1`，让 `.bat` 停下（宁可不出包） |

> 历史：0.1.6-alpha.2 时期上游确无此分支，本地曾用 7 行补丁绕过；升级到 0.1.7-alpha.2 后该补丁正式退役。

### 3.4 同步官方代码后，补丁还要不要再改一遍？—— 不用

本地改动目前只剩 **1 个已跟踪文件、+9 行纯新增**（无删除）：

| 文件 | 新增 | 性质 |
|---|---|---|
| `apps/desktop/installer/window-frame.cpp` | +9 | 本机 SDK 19041 适配（**不是上游 bug**） |

> 0.1.6 时期还有第 2 个补丁（`main.ts` 的 shell 分支）。上游 0.1.7-alpha.2 已自行修复，本地补丁已退役 —— 见 §3.3。

`git pull` / 重下源码会把文件还原成上游版本（补丁一起消失），但**重跑 `.bat` 时第 2 步会自动补回来**。三种情况都已实测：

| 情况 | `prepare-build.cjs` 的行为 |
|---|---|
| 补丁还在 | 跳过（幂等） |
| 被上游代码覆盖，结构没变 | **自动重新补上**（实测 9 行） |
| 上游改写了文件结构，补丁打不上 | 打印警告并提示人工检查（该补丁失效会引发**编译报错**，不会被静默忽略） |

**一句话**：你不需要记住这些补丁 —— 它们由脚本托管，同步官方代码后双击 `.bat` 就自动恢复。

## 7. 常见坑速查

| 症状 | 真因 | 处理 |
|---|---|---|
| 每个请求报 `error (23)` | pnpm 11 默认对 1600+ 条 lockfile 做**供应链复验**，并发拉元数据失败 | 加 `--trust-lockfile`（**不是换源**） |
| 安装静默挂死，零日志 | pnpm 的"是否清理 node_modules"确认在无 TTY 时**死等输入** | `npm_config_confirm_modules_purge=false` + stdin 接空 |
| `MISSING_EXPORT: assertNever` | 旧版本残留的**孤儿包目录** | §3.2，跑 `prepare-build.cjs` |
| `Native installer helper compilation failed`（无细节） | SDK 19041 GDI+ 头文件 + `/W4 /WX` | §3.1，跑 `prepare-build.cjs` |
| `tar: Cannot connect to D:` | PATH 里 Git 的 MSYS `tar` 排在 Windows 自带 `bsdtar` 前面 | 让 `C:\Windows\System32` 在 PATH 中优先 |
| `spawn powershell.exe ENOENT` | PATH 缺 `WindowsPowerShell\v1.0` | 补进 PATH |
| `SAFE_DELETE_BULK_CONFIRM_REQUIRED` | WorkBuddy 注入的 node 删除拦截垫片 | 设 `CODEBUDDY_SAFE_DELETE_ENABLED=0`（仅 AI 会话内需要） |
| 构建报「拒绝访问 (os error 5)」且**每次文件都不一样** | 沙箱随机拦截写文件 | 环境干扰，非真实问题 |
| `pnpm dsh web` 报 `No usable native binding found for node-addon-require-builtin-win32-x64-msvc` | `node_modules/.pnpm/node_modules/`（pnpm 隐藏提升目录）里有**空目录假链接**——安装被中断留下的 | 见 §7.1 |
| `pnpm run dev:desktop` 报 `ENOENT: ... stat '...node_modules\.pnpm\node_modules\@deepseek-ai\dsh-acp-demo'` | 同一处的**死链**：该链接指向 master 已删除的包。`development-project.ts` 会对每个条目调 `realpathSync`，遇死链直接抛 ENOENT | 见 §7.1，跑 `prepare-build.cjs` |
| `pnpm run dev:desktop` 报 `electron.exe: bad option: --remote-debugging-port=...` | 环境里带了 `ELECTRON_RUN_AS_NODE=1`，electron 以纯 Node 模式启动、拒绝 Chromium 参数 | 只会在被注入该变量的自动化会话里出现，你的终端不会有 |
| 点「检查更新」后**界面发白模糊、点不动、任务栏也关不掉** | 上游 `protocol.handle` 只服务 `app` host，`dsh-app://shell/*` 返回 **404 空页** → 透明 modal 盖住被 `blur(2px)` 的父窗口 | §3.3 / §14，跑 `prepare-build.cjs` |

> **鉴别真假 Bug 的口诀**：**报错的文件/工具每次都变 = 环境干扰；稳定复现同一个 = 真实问题。**

### 7.1 「空目录 / 死链」——最隐蔽的一类坑

**症状**：`Cannot find module 'X'`，而 X 明明躺在 `.pnpm/X@版本/` 里；
或 `ENOENT: stat '...node_modules\.pnpm\node_modules\<包>'`；`pnpm install` 却说 "Already up to date" 不修。

**三种坏法**（都源自安装被打断、或 master 删掉了某个包）：

| 坏法 | 成因 |
|---|---|
| **空目录** | 本该是 junction，被打断在"先建目录、后挂链接"之间。Node 找得到目录却找不到文件 |
| **死链** | 链接目标已被删除（多为 master 移除的 workspace 包，如 `dsh-acp-demo`）。`realpathSync` 直接抛 ENOENT |
| **指向残留** | 目标目录还在但没有 `package.json`（旧布局残留，如 `native/landlock-run`、`examples`），后续 `readManifest` 抛 ENOENT |

**为什么容易漏**：只扫顶层 `node_modules` 不够，必须连这些一起扫：

```
node_modules\.pnpm\node_modules\          ← pnpm 隐藏提升目录，最容易中招
node_modules\.pnpm\node_modules\@scope\   ← ⚠️ scoped 包在这一层，只扫一层会全漏掉
node_modules\.pnpm\*\node_modules\
apps\*\node_modules\、packages\*\*\node_modules\
```

**判据**：条目是**真实目录且为空** = 坏；是**链接但目标不存在 / 目标无 `package.json`** = 坏。
跳过 `.ignored_*`（pnpm 的正常标记）和 `.bin`。

**处理**：删掉这些坏条目（内容本就是空的/失效的，删除不丢东西）。
⚠️ **不要试图猜"该链到哪个版本"**：同名多版本时 pnpm 按依赖图择优，实测
「被依赖最多，并列取高版」这条规则只命中 **6/13**，猜错会**静默解析到错误版本**（比报错更难查）。

**现成工具**：
- `prepare-build.cjs` 第 4 步已内置该检查（**只删不建**，零风险），`.bat` 每次都会跑
- `D:\codes\deepseek-harness-desktop-build\probes\audit-hoisted-links.cjs` —— 完整审计 + 分类处置（`--apply` 才动手）
- `D:\codes\deepseek-harness-desktop-build\probes\verify-dev-mirror.cjs` —— 不启动 Electron 就能复现 `dev:desktop` 的这条失败

**已实测**：清完 312 空目录 + 88 个 workspace 死链/残留后，`pnpm dsh web`（3080）与
`pnpm run dev:desktop`（19387 + DevTools 9222/9229）均恢复正常。

## 11. 附录：删代码 / 重下仓库时，哪些不能删

**先说结论**：`install-deepseek-desktop.bat` 和 `prepare-build.cjs` **就住在仓库根目录里**，
所以「把代码文件全删掉重下」会把**工具本身一起删掉**。删之前务必看清楚下面这张表。

### 🔴 必须保留（否则 .bat 跑不起来）

| 文件 / 目录 | 原因 |
|---|---|
| `install-deepseek-desktop.bat` | 工具本体。删了就没得跑了 |
| `prepare-build.cjs` | 必须与 `.bat` **同目录**（脚本用 `%~dp0` 找它）；而且它内部把**自身所在目录**当作仓库根（代码里是 `__dirname`），所以**必须放在仓库根目录**，搬到别处会认错路径 |
| `.git\` | 构建里的 `scripts/build.ts` 会执行 `git rev-parse HEAD` 取 commit hash，取不到就直接抛 `Command failed: git rev-parse HEAD`。**本版 .bat 已加兜底** —— 检测不到 git 或 `.git` 时自动填占位 hash，因此这条已从"必须"降级为"建议保留" |
| 系统 PATH 里的 `git` 可执行文件 | 同上一行，同一条兜底覆盖。注意它在**仓库之外**，是系统安装的 |

> 兜底实测结论（用没有 `.git` 的目录直接调那个函数）：
> 不设 `DSH_CLIENT_COMMIT_HASH` → 抛 `Command failed: git rev-parse HEAD`；
> 设了 → 正常返回，构建继续。所以**只要保留这份新版 .bat，删掉 `.git` 也能构建**。

### 🟡 建议保留（纯粹为了省时间）

| 文件 / 目录 | 删了的代价 |
|---|---|
| `apps\desktop\.desktop-build\downloads\`（约 241 MB） | Electron / Node / Python 运行时的下载缓存，删了要重新下载 |
| `node_modules\`（各层） | `pnpm install --force` 会重建。包体存在仓库外的 `D:\.pnpm-store\v11`（约 8.5 GB），**不会重新下载**，但重链要 10–30 分钟 |
| `apps\desktop\.desktop-build\targets\`（约 2.6 GB） | 打包中间产物，删了重跑要重做一遍 |

### 🟢 可以放心删（会自动重建）

| 文件 / 目录 | 重建方式 |
|---|---|
| `apps\desktop\.env.windows` | `.bat` 里有 `if not exist ... copy`，自动从 `.env.windows.example` 重建 |
| 全部源码、`pnpm-lock.yaml` | 跟随重新下载 |
| `lib\`、`dist\`、`*.tsbuildinfo` | 重新编译生成 |
| `window-frame.cpp` 的 SDK 补丁 | `prepare-build.cjs` 幂等重打 |

### ⚪ 删了就没了（不影响 .bat 运行，但你会失去它们）

| 文件 | 说明 |
|---|---|
| `README-安装说明.md` | 本文件 —— 建议先复制出来 |
| 已构建好的 `*.exe` 安装包、`win-unpacked\` | 要重新构建（约 20–40 分钟） |

### 推荐的两条操作路径

| 方案 | 做法 | 适合 |
|---|---|---|
| **A. 只想更新到最新代码**（推荐） | **别删**，用 git：`git fetch` + `git reset --hard origin/master` | 常规升级 |

> `downloads\` 只是重下。真正**不能丢**的只有那两个脚本。

## 12. 附录：重跑构建会覆盖什么

**一句话**：**不需要手动删任何东西** —— 该清的在构建流程里都清了；但**旧安装包不保证保留**，想留就先复制出去。

| 产物 / 目录 | 重跑时的行为 | 依据 |
|---|---|---|
| `unsigned-artifacts\*.exe` | **会被替换 / 不保证保留** | 实测：新旧包在同一路径同名共存不可靠，务必先备份 |
| `unsigned-artifacts\win-unpacked\` | 清空重建 | 实测被清成空目录后再填充 |
| `unsigned-artifacts\*.blockmap` | 被新版覆盖（`differentialPackage: true`） | `electron-builder-config.mjs:199` |
| `targets\win-x64\packed\landlock\` | **先 `rmSync` 再重建** | `package-target.ts:351` |
| `targets\win-x64\dsh\`、`dsh-pnpm\` | **先 `rmSync` 再重建** | `prepare-dsh.ts:109-110` |
| `targets\win-x64\{runtime,electron,package-set}\` | 复用 / 按需刷新，**不重新下载** | `desktop-build-paths.mjs` |
| `.desktop-build\downloads\` | **保留复用**（代码注释写明是 shared immutable download cache） | 同上第 54 行 |
| `.desktop-build\packaging-runs\` | **只增不减** —— 每次运行新建一个 `<时间戳>-<随机>` 目录 | `packaging-run.mjs:66` |
| `%TEMP%\dsh-desktop-runtime-*` | 每次新建临时目录，成功或失败后清理 | `prepare-dsh.ts:17` |
| 各层 `node_modules` | `pnpm install --force` 重建（包体在仓库外的 store，不重下） | `.bat` 第 3 步 |
| `lib\`、`dist\` | 重新生成（vite 会先清 `apps/web/dist`） | `build:lib` / `build:web` |
| `*.tsbuildinfo` | **被 `prepare-build.cjs` 主动删掉** → 每次都是全量编译 | `prepare-build.cjs` 第 2 步 |
| `apps\desktop\.env.windows` | **保留**（不存在才从 example 复制） | `.bat` 里 `if not exist ... copy` |
| `window-frame.cpp` 的 SDK 补丁 | **保留**（幂等，已打则跳过） | `prepare-build.cjs` 第 1 步 |
| `install-deepseek-desktop.bat`、`prepare-build.cjs`、本文件 | **保留**（构建不碰仓库根） | — |

**两个要注意的点**：

1. **旧安装包想留就先复制出去**。文件名带版本号（`deepseek-harness-<版本>-win-x64.exe`），
   换版本时文件名会变，但**不要依赖旧文件会自动留着**。
2. **`packaging-runs\` 会越攒越多**（每次一个目录，含 `stdout.log`/`stderr.log`）。
   排错时它很有用，但堆积多了可以整目录删掉 —— 它只是日志，删了不影响任何东西。

**为什么每次都是全量编译**：`prepare-build.cjs` 会主动删掉根目录的 `*.tsbuildinfo`。
这是故意的 —— 陈旧的增量状态会让 `tsc -b` 跳过重建，产生过期的 `lib/` 产物
（早期 `MISSING_EXPORT` 那个坑就是这么来的）。代价是每次构建都慢一些，但结果可靠。

## 13. 附录：装好的应用「界面发白、点不动、关不掉」—— 更新通道配错了

**这是本地构建最容易踩的坑，而且症状极具误导性。**

### 症状

| 现象 | 说明 |
|---|---|
| 窗口画面**发白/像蒙了一层** | 整窗口上盖了一层遮罩 |
| 什么都点不动 | 遮罩把点击全吃了 |
| 任务栏「关闭窗口」无效，只能任务管理器 | 遮罩层挂在主窗口上 |
| 有时停在 `HARNESS / Loading plugins…` 不动 | 更早期的一层表现 |

⚠️ **别被带偏**：它不是崩溃、不是缺依赖、也不是端口冲突。日志里**干干净净**，
因为这条错误路径走的是 UI 遮罩、不打印日志。

### 根因链条

1. 打包时 `.env.windows` 里是 `DSH_DESKTOP_AUTO_UPDATE_ENV=test`
2. `apps/desktop/scripts/desktop-policy-environment.mjs` 里写死了：
   ```js
   authentication: deployment === 'test' ? 'feishu-test' : 'anonymous'
   ```
3. 于是这个配置被打进安装包的 `package.json`（`dshMandatoryUpdatePolicy`）
4. 每次启动，应用请求：
   ```
   GET https://harness-test.deepseek.com/api/v0/check_client_update?scenario=launch
   → HTTP 401  {"error":{"code":"UNAUTHENTICATED","message":"feishu auth required"}}
   ```
5. 客户端把它当作 `authentication-required` → `main.ts` 调用 `queuePolicyAuthentication()`
6. → `runPolicyAuthentication()` 第一句就是
   ```js
   updateDialog.show(parent, { title: messages.policyLoginTitle, buttons: [policyLogin, later], cancelId: 1 })
   ```
7. → **`updateDialog.show()` 会在主窗口上盖一个 `dsh-app://shell/update-dialog.html` 覆盖窗口**
   （`update-dialog.ts` 的注释原文：*Window blocked by this confirmation*）
8. 这个遮罩在本地环境里**渲染不出内容**（DOM 实测 `<body></body>`，一个按钮都没有），
   于是就是"发白 + 点不动 + 关不掉"

**结论：本地未签名构建永远过不了飞书 SSO，所以 test 通道必然卡在登录遮罩上。**

### 修法

把更新通道改成 `production`（走 `authentication: 'anonymous'`，不会弹登录遮罩）：

```ini
# apps/desktop/.env.windows
DSH_DESKTOP_AUTO_UPDATE_ENV=production     # ← 不要用 test
DSH_DESKTOP_MANDATORY_UPDATE_PROD_ORIGIN=https://harness.deepseek.com
```

然后**只需重跑打包**（不用重装依赖）：

```bat
cd /d D:\codes\deepseek-harness
pnpm run package:desktop:win:x64:unsigned
```

> `prepare-build.cjs` 第 5 步已内置该检查：发现是 `test` 会**自动改成 `production`** 并提示。
> 为什么需要自动改 —— `.env.windows` 一旦被删，`.bat` 会从 `.env.windows.example` 重新生成，
> 而 example 里正是 `test`，这个坑就会回来。

### 排查手法（安装版不带 DevTools 时怎么查）

安装版默认没有开发者工具、日志也干净，但可以用 Chromium 开关从外部看：

```bat
cd /d "D:\software-install\DeepSeek Harness"
DeepSeek Harness.exe --remote-debugging-port=9222
```

然后 `curl http://127.0.0.1:9222/json/list` 就能列出所有渲染目标。
**"多出来的那个窗口"往往就是元凶** —— 本次就是靠它发现 `dsh-app://shell/update-dialog.html`
这个不该存在的遮罩。配合 CDP 的 `Runtime.evaluate` 还能读 DOM、调 `window.close()`。

参考脚本：`D:\codes\deepseek-harness-desktop-build\probes\cdp-probe.cjs`（读各目标 DOM/可见性）、`cdp-escape.cjs`（试着关遮罩）。

> 顺带：在打上 §3.3 的补丁之前，这个遮罩**不响应 Esc**（页面是 404 空页，连 JS 都没有），
> 只能重建包；补丁之后遮罩里有正常的「确定」按钮，可以直接点掉。

## 14. 附录：点「检查更新」就发白卡死 —— 曾是上游缺陷，**0.1.7-alpha.2 已官方修复**

> **状态（2026-09-23）**：上游在 **0.1.7-alpha.2** 已自行修复，代码与本地当年的补丁**逐字一致**。
> 本地补丁已退役（详见 §3.3）。本节保留作为**排查手册** —— 万一将来上游又回退，
> 症状、根因链条与取证手法都仍然适用；`prepare-build.cjs` 第 6 步也会在校验失败时报警。

**这是与 §13 不同的另一个原因**，两者都会表现为"空白遮罩"，但根子不一样：

| | §13 更新通道配错 | §14 本篇：壳页面没被服务 |
|---|---|---|
| 触发 | 启动时 | 点「检查更新」/ 强制更新 / 策略登录 |
| 遮罩里本该有什么 | 「需要飞书登录」确认框 | 检查结果 / 安装确认框 |
| 真因 | 策略接口返回 401 | `dsh-app://shell/*` 返回 **404 空页** |
| 状态 | 已修（channel 改 production） | **上游 0.1.7-alpha.2 已修** |

### 症状

- 点设置里的「检查更新」→ **整个界面发白、发虚**，像"前面有个窗口把后面糊住了"
- 点不动任何东西（包括主窗口的关闭按钮）
- 任务栏右键关闭也没反应，**只能进任务管理器杀进程**
- 强制更新、策略登录对话框：同样表现

### 为什么"发白"和"关不掉"都是设计出来的

`apps/desktop/src/update-overlay.ts`：

```ts
const window = new BrowserWindow({
  parent, modal: true, show: false, frame: false, transparent: true,
  ...parent.getContentBounds(), resizable: false, skipTaskbar: true, ...
})
// 故意给父窗口加模糊：
parent.webContents.insertCSS('body { filter: blur(2px) !important; }')
```

- `transparent + 覆盖父窗口全幅` → 你能"看穿"它，看到的其实是**被模糊的父窗口**
- `modal: true` → 父窗口被阻塞，点不动；连标题栏的 X 也失效
- `skipTaskbar: true` → 它自己不在任务栏，你找不到它
- 页面是空白 → 没有「确定」可点 → **只能杀进程**

所以只要这个壳页面加载不出来，**任何**更新相关对话框都会变成一个"看不见又关不掉的罩子"。

### 根因：`protocol.handle` 只认 `app` 这个 host

`apps/desktop/src/main.ts`（上游原样）：

```ts
protocol.handle(SCHEME, (request) => {
  const url = new URL(request.url)
  if (url.hostname === 'app') { /* 主界面 */ }
  return Promise.resolve(new Response(null, { status: 404 }))   // ← 其余全 404
})
```

而三种对话框都从 `shell` host 加载页面：

| 页面 | 出处 |
|---|---|
| `dsh-app://shell/update-dialog.html` | `update-dialog.ts`（检查更新 / 安装确认） |
| `dsh-app://shell/mandatory-update.html` | `mandatory-update-window.ts`（强制更新） |
| `policy-login-loading.html` | `policy-test-auth.ts`（策略登录） |

**证据**：
- 打包产物 `resources/app.asar` → `lib/main.js` 里只有 `hostname === "app"` 一个分支
- 壳页面文件**确实在包里**（`renderer/update-dialog.html` 963 B、`update-dialog.js` 2090 B……），
  也就是说"文件打进去了，但没人提供它"
- 上游 master（含最新提交）**同样没有**这个分支 —— 属于产品缺陷，不是本地构建失误
- 单测抓不到：`apps/desktop/tests/update-dialog.spec.ts` 把 `loadURL` mock 成了空函数

### 修法（7 行，不动业务逻辑）—— 上游已采用同一写法

```ts
// apps/desktop/src/main.ts，protocol.handle 内（0.1.7-alpha.2 上游自带）
if (url.hostname === 'shell') return serveWebDocument(request, join(app.getAppPath(), 'renderer'))
```

`serveWebDocument` 与主界面用的是**同一个**函数（主界面读的是 asar 里的 `dsh-web-frontend/dist`，
机制完全相同），所以打包后同样能读到 asar 内的 `renderer/`。
