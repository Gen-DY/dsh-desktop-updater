## 设计要点（先说清楚为什么这么写）

### 1. 为什么不接收路径参数

产品文档（网页）**无权选择产物**。如果 API 设计成 `useLocalBuild(dir)`，等于让网页读取任意目录，直接违背官方安全模型：

> `ipc.ts:61` *"Product documents cannot supply update versions, package URLs, or installation authorization."*

所以 API **零参数**：渲染进程只能表达"用本地构建更新"这个**意图**，具体目录由主进程自己决定。

### 2. feed 目录：`~/.dsh/desktop-updates/`（已定稿）

```
C:\Users\<用户>\.dsh\desktop-updates\
    nightly.yml
    deepseek-harness-<版本>-win-x64.exe
```

用 `dshHomePath('desktop-updates')` 解析 —— 跟随 `DSH_HOME` 环境变量覆盖，不写死绝对路径。
由**构建脚本**（外部，L1）在构建完成后写入。主进程只读，不接收外来路径。

选它的理由见文末 **附录 A**。

### 3. 主进程只做三件事

```
起本地 HTTP 服务（端口自动分配 listen(0)，避免冲突）
  → autoUpdater.setFeedURL() 临时切到本地
  → 复用已有 openUpdatePrompt()   ← 关键：下载/停任务/退出/装/重启全走官方既有流程
```

**不新增任何下载或安装逻辑。**

### 4. 为什么不用改 `update-coordinator.ts`

`main.ts:493` 构造时用的是默认参数：

```ts
const updates = new DesktopUpdateCoordinator(publishUpdate, async () => { ... })
// 第三个参数 updater 默认 = autoUpdater（electron-updater 全局单例）
```

主进程对**同一个单例**调 `setFeedURL()` 即可生效，无需让 coordinator 暴露任何东西。

### 3b. handler 与本地 feed 服务（插在 `:660` 的 `updatesOpen` handler 之后）

```ts
  /**
   * Feed directory produced by a local build. Main-process-owned: the renderer
   * can ask to use a local build, never point at one.
   * Lives under the shared Harness home so one relocation (`DSH_HOME`) moves it too.
   */
  const localBuildFeedDirectory = (): string => dshHomePath('desktop-updates')

  /** Serve that directory on a loopback port. `listen(0)` avoids any fixed-port conflict. */
  const startLocalBuildFeed = (): Promise<{ port: number; close: () => void }> => new Promise((resolve, reject) => {
    const directory = localBuildFeedDirectory()
    let server: Server
    server = createServer((request, response) => {
      const name = new URL(request.url ?? '/', 'http://127.0.0.1').pathname.replace(/^\/+/, '')
      // Flat directory only: no separators, no traversal, no directory listing.
      if (name === '' || name.includes('/') || name.includes('\\') || name.includes('..')) {
        response.writeHead(404).end()
        return
      }
      readFile(join(directory, name)).then(
        body => response.writeHead(200, {
          'content-type': name.endsWith('.yml') ? 'text/yaml' : 'application/octet-stream',
          'content-length': String(body.byteLength),
        }).end(body),
        () => { response.writeHead(404).end() },
      )
    })
    server.on('error', reject)
    server.listen(0, '127.0.0.1', () => {
      const address = server.address()
      if (address === null || typeof address === 'string') {
        server.close()
        reject(new Error('desktop update: local build feed did not bind'))
        return
      }
      resolve({ port: address.port, close: () => { server.close() } })
    })
  })

  ipcMain.handle(DESKTOP_IPC.updatesLocalBuild, async (event) => {
    assertProductSender(event)
    const directory = localBuildFeedDirectory()
    if (!existsSync(join(directory, 'nightly.yml'))) {
      // Loud, and actionable: there is nothing to install until a local build has run.
      throw new Error(`desktop update: no local build feed at ${directory} — run the local build first`)
    }
    const feed = await startLocalBuildFeed()
    const previousUrl = autoUpdater.getFeedURL()
    autoUpdater.setFeedURL({ provider: 'generic', url: `http://127.0.0.1:${feed.port}/`, channel: 'nightly' })
    updateJournal?.action('local-build-feed')
    try {
      await openUpdatePrompt(true)
    } finally {
      feed.close()
      // Restore the packaged feed so a cancelled local install does not strand this process on loopback.
      if (previousUrl !== null) autoUpdater.setFeedURL({ provider: 'generic', url: previousUrl, channel: 'nightly' })
    }
  })
```

## 已知限制（先讲清楚，避免上线后才发现）

| 限制 | 原因 | 对策 |
|---|---|---|
| **同版本无法重装** | electron-updater 按 semver 比对，版本相同即"已是最新" | 构建时给版本号加后缀（`buildVersion`），或接受"只有官方发新版才构建" |
| **刚做完方式一更新后立刻用方式二** | coordinator 的 `downloaded` 已置位，`check()` 会直接返回缓存状态 | 提示用户重启应用；或首次进入方式二前不做方式一更新 |
| **`app-update.yml` 必须存在** | `update-coordinator.ts:53` 的 `enabled()` 会检查该文件 | **P2 是前置条件**，方式一方式二都依赖 |
| 本地 feed 服务仅回环 | 安全设计 | 无需对策；不对局域网暴露 |

## 安全复述（为什么这样设计是安全的）

| 攻击面 | 防护 |
|---|---|
| 网页指定任意目录 | API **零参数**，目录由主进程 `app.getPath('userData')` 决定 |
| 路径穿越（`../`） | 文件名白名单校验：拒绝含分隔符与 `..` |
| 目录遍历 | 不实现列表，仅按名取单文件；不存在即 404 |
| 局域网窃听/投毒 | 仅绑 `127.0.0.1`；端口由内核分配，不固定可预测 |
| 伪装来源 | `assertProductSender(event)`：校验 sender 必须是主窗口顶层 frame |

## 附录 A：为什么 feed 目录定在 `~/.dsh/desktop-updates/`

### 候选对比

| 候选 | 好找 | 跟随 `DSH_HOME` | 与 DSH 数据同处 | 判定 |
|---|---|---|---|---|
| `%APPDATA%\dsh-desktop-updater\local-feed` | ❌ `%APPDATA%` 在资源管理器里**默认隐藏** | ❌ | ❌ | 否 |
| **`~/.dsh/desktop-updates`** | ✅ `.dsh` 在 Windows 上**可见**（见下） | ✅ | ✅ | **选定** |
| `~/.dsh-desktop-updater` | ✅ | ❌ | ❌ | 多一个顶级目录，认知负担 |
| 源码仓库内 `<repo>/.local-feed` | — | ❌ | ❌ | 安装版机器未必有源码仓库 |

### 四条理由

1. **符合 DSH 自己的设计约定。** `packages/util/home-paths/src/index.ts` 注释原文：
   > *The harness keeps all user data under one root.*

2. **跟随 `DSH_HOME`。** 用 `dshHomePath('desktop-updates')` 解析（优先级：显式配置 > `$DSH_HOME` > `~/.dsh`）。
   用户改了 home 位置，feed 目录自动跟随，不写死绝对路径。

3. **比 `%APPDATA%` 好找。** Windows 的隐藏是**文件属性位**，以 `.` 开头**不等于**隐藏——
   `C:\Users\<用户>\.dsh` 在资源管理器里直接可见；而 `%APPDATA%` 是真正隐藏的。
   这直接对应"用户维护便捷"这个诉求。

4. **不干扰官方结构。** 与 `profiles/`、`cache/`、`settings.yaml` **平级**，不塞进它们内部，
   也不占用官方命名。

### 维护性加分

`useLocalBuild()` 在 feed 缺失时抛出的错误信息**带完整路径**（`no local build feed at <路径>`），
用户在错误对话框里就能看到该去哪找、往哪放。
