## 2. 这个工具受官方更新影响有多大？

**结论：比原先估计的小得多——方式一可以做到「零内核改动」，只有方式二需要动 2 个文件。** 详见 2.1~2.3。

### 2.1 接触面清单与稳定性评级

| 层 | 接触对象 | 改什么 | 官方改动频率 | 升级影响 |
|---|---|---|---|---|
| **L1 零影响** | 环境预检、构建编排、本地 feed、兼容性校验 | **外部脚本，不 import 内核任何代码** | — | **零** |
| **L2 低** | `electron-builder-config.mjs:92,240` | unsigned 也让 `publish` 非 null | 低（打包脚本，结构稳定） | 需重新确认位置 |
| **L2 低** | `packages/client/ui-settings-*` | 用 `ctx.slots.register()` 注册更新面板 | 低（公开扩展点） | 需重新确认 slot 名 |
| **L3 中** | `apps/desktop/src/ipc.ts` | 加 IPC 通道 + 扩 `DshDesktopProductApi` | 中 | 需跟着改 |
| **L3 中** | `apps/desktop/src/preload-app.ts` | 暴露新 API | 中 | 同上 |
| **L3 中** | `apps/desktop/src/main.ts` | 注册 IPC handler | 中 | 同上 |
| **L4 高** | `update-coordinator.ts` | 加 `building` 阶段（**可选**） | 高（更新核心） | **尽量别动** |
| **L4 高** | `renderer/update-dialog.*` | 改确认框 UI（**可选**） | 高 | **尽量别动** |

### 2.2 三个 L3 文件是什么、干什么

它们是 **Electron 标准三层结构**的一段：

```
渲染进程 renderer（浏览器环境）
   DSH Web UI + 客户端插件 —— 只能调 window.dshDesktop.*
        ↕  preload-app.ts 用 contextBridge 暴露
预加载桥 preload-app.ts
   把主进程的能力包装成页面能调的 JS 对象
        ↕  ipcRenderer.invoke(通道名)   ← 通道名定义在 ipc.ts
主进程 main.ts（Node / Electron 主进程）
   electron-updater · 文件系统 · 子进程
```

| 文件 | 行数 | 作用 | 现有相关内容 |
|---|---|---|---|
| `src/ipc.ts` | 87 | **前后端的「合同」**：定义所有 IPC 通道名常量 + `DshDesktopProductApi` 类型（前端能调什么） | `:17-19` updates 三条通道；`:61-70` 产品 API 类型 |
| `src/preload-app.ts` | 70 | **桥**：用 `contextBridge.exposeInMainWorld('dshDesktop', …)` 把能力暴露给页面 | `:16-24` updates 的三个方法，**每个都是一行 `ipcRenderer.invoke`** |
| `src/main.ts` | 1119 | **实现**：注册 IPC handler、持有 coordinator、操作窗口与文件系统 | `:493` `new DesktopUpdateCoordinator`；`:653/:657` 注册 `updatesStatus` / `updatesOpen` |

**对应你哪个需求**：只有**方式二的「本地 feed + 安装」**需要它们。方式一不需要（见 2.3）。

### 2.3 重大优化：方式一零内核改动

查证 `main.ts:664` 的 `openUpdatePrompt()` —— 它**本身就是完整的一键流程**：

```
updates.check()  →  无更新 → 提示「已是最新」
                 →  检查失败 → 展示失败原因
                 →  有更新 → 确认后 download() → install()（quitAndInstall）
```

而它**已经有前端 API**：`window.dshDesktop.updates.open()`（`preload-app.ts:18` → `ipc.ts:18` → `main.ts:657`）。

**feed 地址由打包时的 `app-update.yml` 决定**，不需要运行时切换。

→ **只要打包时把 feed 指向你的 GitHub 仓库，调 `updates.open()` 就全自动了。方式一不需要改任何内核文件。**

另外两项也都是零内核：

| 功能 | 怎么做 | 为什么零内核 |
|---|---|---|
| 显示官方版本 | 客户端插件 `fetch` npm registry | **实测两个 registry 都支持 CORS**（`npmjs` 返回 `*`，`npmmirror` 回显 Origin） |
| 显示我的仓库版本 | 读 `updates.status()` | 返回的 `DesktopUpdatePresentation` 已含 `phase` 与 `version` |

**方式二才需要动文件**，而且很轻：

| 文件 | 加什么 |
|---|---|
| `ipc.ts` | 1 条通道常量 + API 类型里加 1 个方法 |
| `preload-app.ts` | 1 行转发 |
| `main.ts` | 1 个 handler（起本地 feed 服务 → `autoUpdater.setFeedURL()` → 复用已有 `openUpdatePrompt()`） |

**注意：不需要改 `update-coordinator.ts`** —— `main.ts` 里 `new DesktopUpdateCoordinator(publishUpdate, beforeRestart)` 用的是默认参数 `updater = autoUpdater`（electron-updater 的全局单例），所以 `main.ts` 直接对同一个单例 `setFeedURL()` 即可。

### 2.4 还能再优化吗？—— 一处待定

「预检 / 兼容性校验 / 构建」这三个是**长任务或子进程**，渲染进程跑不了，需要一个触发通道。三个选项：

| 选项 | 做法 | 内核成本 |
|---|---|---|
| **C（建议先做）** | 保持脚本化（双击 bat / 命令行），UI 只显示**状态与指引** + 提供命令复制 | **零** |
| B | 桌面端再加 1 条 IPC（`runJob`） | 同方式二，再动那 3 个文件 |
| A | 宿主插件 + Typert remote 服务 | 需改 `packages/api/remotes` 组装层——README 明确写着「**若要增加能力，必须显式导入相应的 `/remote` 值并在此组合中挂载**」 |

**建议先走 C**：符合脚本化偏好，"点按钮跑 60 分钟构建"本身也不是好交互（构建更适合后台/终端）。等 UI 稳定再考虑 B。

### 2.5 三条降低影响的设计原则

1. **能放外部脚本的一律放外部**（L1）。预检、构建、feed、兼容性校验都是独立 Node 脚本，通过命令行与 DSH 交互，**不 import 内核代码**。官方怎么改都影响不到它们。
2. **能用公开扩展点的就用**（L2）。UI 面板尽量做成客户端插件走 `ctx.slots.register()`，而不是改 `renderer/`。
3. **L4 的两个文件尽量不碰**。
   - `update-coordinator.ts`：构建是个长任务，硬塞进它的 `phase` 枚举会污染语义，也要跟着上游改。**改为独立进度通道**。
   - `renderer/update-dialog.*`：它只是确认框，不是面板。**面板走客户端插件，确认框保持原样。**

**按这个设计，真正的"内核改动"只有 L3 的三个文件（出入口），其余全在外部。**官方发版时的适配工作量：通常就是重新确认几个锚点位置。

## 3. 兼容性校验（你问的第 2 点）

### 3.1 检测：完全可行，而且你已经有现成范式

你的 `prepare-build.cjs` 里已经写了两个成熟的"锚点校验"：

```js
// 第 1 步：SDK 补丁
const pattern = /#include <dwmapi\.h>[ \t]*\r?\n#include <gdiplus\.h>/
if (!pattern.test(src)) {
  if (upstreamFixed) console.log('上游自行修复，跳过')
  else console.log('⚠️ 结构与预期不符，未做修改')   // 提示人工检查
}
```

```js
// 第 6 步：shell 协议分支 —— 三级处置，最完整
if (src.includes(shellMark))                    → 上游已提供，跳过
else if (src.includes(anchor))                  → 自动补回补丁
else                                            → exit 1，让流程停下（宁可不出包）
```

**第 6 步就是标准答案**：检查 → 分级处置 → 兜底失败要 loud。把它推广到所有接触点即可。

### 3.2 要校验的锚点清单

| # | 目标 | 锚点 | 期望形态 |
|---|---|---|---|
| 1 | `window-frame.cpp` | `#include <dwmapi.h>` + `#include <gdiplus.h>` 相邻 | 存在 → 打 SDK 补丁 |
| 2 | `main.ts` | `protocol.handle(SCHEME)` 区域含 `hostname === 'shell'` | 存在 → 跳过；缺失 → 补 |
| 3 | `ipc.ts` | `DESKTOP_IPC` 常量表、`DshDesktopProductApi` 接口 | 存在 → 追加自己的通道 |
| 4 | `preload-app.ts` | `contextBridge.exposeInMainWorld` 调用点 | 存在 → 追加暴露 |
| 5 | `electron-builder-config.mjs:92` | `unsigned ? undefined : resolveDesktopAutoUpdateConfig(...)` | 存在 → 改为 unsigned 也给 publish |
| 6 | `update-coordinator.ts` | `enabled()` 的 `app-update.yml` 判断 | **只读校验**，不改 |
| 7 | `renderer/update-dialog.js` | `api.subscribe` / `api.status` | **只读校验**，不改 |

### 3.3 自动修复：有明确边界，不能过度

| 情形 | 能否自动 | 处置 |
|---|---|---|
| 上游已自带该修复 | — | ✅ 自动跳过（正常路径） |
| 锚点仍在，只是位置/缩进变了 | ✅ 能 | 正则容错 + 自动补回 |
| 锚点被上游改动但语义可推断 | ⚠️ 部分 | 尝试补回，**补完必须自检**，自检失败则升级为失败 |
| 上游重构了该区域（锚点失配） | ❌ **不能** | **fail loudly** + 产出诊断包（见 3.4） |

**关键原则（你 skill 里已经记过）：**

> **「失效后不报错的补丁，必须 fail loudly」** —— 这类补丁失效不会引发编译错误，静默跳过就会产出坏包。

所以**"全自动兼容性修改"是危险目标**。正确目标是：**能自动的自动，不能的必须停，并且停得有信息量。**

### 3.4 诊断包：你要的"丢给 AI 改"，做成结构化输出

校验失败时，`verify-compat.cjs` 输出一份这样的报告：

```markdown
## 兼容性校验失败：3 项

### ✗ main.ts — shell 协议分支锚点失配

- 文件：apps/desktop/src/main.ts
- 期望：protocol.handle(SCHEME) 区域内存在 hostname === 'shell' 分支
- 实际：区域内未找到该判断，且 anchor 也不匹配
- 影响：点「检查更新」会盖一层空白遮罩，界面发白、点不动
- 上游本次改动：
  <git diff 摘要，涉及该方法的部分>
- 相关上下文（第 540-575 行）：
  <代码片段>
- 建议：确认上游是否已用其他方式处理 shell host；若是，调整校验条件；若否，手工补分支
```

这份报告**直接可以喂给 AI**（或你自己看）。这就是你要的"丢给 AI 去做修改"。

### 3.5 触发时机

用户选**方式二**时，**拉完源码、构建之前**自动跑一次：

```
拉取/更新源码 → verify-compat → ┬─ 全部通过 → 继续构建
                                ├─ 有警告   → 展示，可继续
                                └─ 有失败   → 阻断 + 展示诊断包 + [导出诊断] / [交给 AI 处理]
```

## 4. 界面信息结构与整体架构

### 4.1 信息分层（v2 修正）

初版 demo 把「检查官方更新」和「从我的仓库下载」混在同一个面板里，概念不清。修正为**三层信息**：

| 层 | 内容 | 是否常驻 |
|---|---|---|
| **① 官方版本** | 上游事实：官方最新版本 vs 当前安装 | ✅ **常驻**，不随方式切换 |
| **② 方式一面板** | 差异：**我的仓库有没有构建好的包、是哪个版本** | 仅方式一 |
| **③ 方式二面板** | 差异：**本地是否满足构建条件** | 仅方式二 |

这样两种方式的差别被正确抽象：**官方版本是共同目标，"怎么拿到它"才是两种方式的区别。**

### 4.2 官方版本的数据源（已实测）

```
npm registry · @deepseek-ai/dsh · dist-tags
  latest: 0.1.5-rc.3     ← 稳定线
  next:   0.1.7-rc.1     ← 候选线（release candidate）
  alpha:  0.1.7-alpha.2  ← 内测线
```

| 特性 | 说明 |
|---|---|
| 直连可用 | ✅ 实测 `registry.npmjs.org` 无需代理 |
| 国内镜像 | ✅ npmmirror 可用 |
| 不依赖 GitHub | ✅ 对"同事环境"尤其重要（他们未必有代理） |

**判定规则：不绑定任何渠道，取官方所有已发布版本里 semver 最高的那个。**

```
semver 排序（prerelease 优先级：alpha < beta < rc < 正式版）
0.1.7-rc.1   >   0.1.7-alpha.2   >   0.1.5-rc.3
   ↑ next           ↑ alpha           ↑ latest
```

> ⚠️ **不要"跟随当前构建线"。** 早先版本按"我构建的是 alpha，就只比 alpha 线"来写，
> 结果官方推进到 `0.1.7-rc.1`（tag `next`）后**完全漏报** —— 因为 `alpha` 这条线的最新
> 还停在 `0.1.7-alpha.2`，按它比较会一直显示"已是最新"。
> **渠道是官方的发布策略，会新增、会变；semver 才是客观顺序。**
> （另注：渠道名不是固定的。`next` 这个标签就是 2026-09-23 发 `0.1.7-rc.1` 时才出现的，
> 所以**不要硬编码渠道列表**，应该把 dist-tags 里出现的全部渠道都读出来。）

界面应把**三条线都列出来**，并标出哪条比当前安装的新：

| 渠道 | 版本 | 相对当前安装（`0.1.7-alpha.2`） |
|---|---|---|
| latest（稳定） | 0.1.5-rc.3 | 更旧（semver 更低） |
| next（候选） | 0.1.7-rc.1 | **更新** ← 应提示 |
| alpha（内测） | 0.1.7-alpha.2 | 相同 |

**一个附带效果**：如果官方发了不带 prerelease 后缀的正式版（如 `0.1.7`），
它的 semver 高于所有 prerelease，会被自动选为最新 —— 这正是期望行为。

### 4.3 方式一的三个状态（不只是"有没有包"）

| 状态 | 界面表现 |
|---|---|
| **无构建** | 「暂无可用构建」+ 引导切换到方式二 |
| **有构建但落后** | 「落后 N 个版本」+ 提示可先装旧版，或改用本地构建拿最新 |
| **与官方同步** | 「已同步」 |

**为什么必须体现**：作者的构建**可能滞后于官方**（官方发了新版但他还没构建）。这是分发模式的固有问题，界面不体现，用户会误以为"方式一给的就是最新"。

### 4.4 方式二的处理

即使官方无更新，**也应允许构建**（用户可能就是想用自己构建的版本，例如改了配置或加了扩展），但需提示「官方无更新，构建后版本不变」。

### 4.5 整体架构

```
                        ┌─────────────────────────────────────┐
                        │  更新面板（显式分流）                │
                        └──────────────┬──────────────────────┘
              ┌────────────────────────┴────────────────────────┐
              ▼                                                 ▼
   ┌─────────────────────┐                        ┌─────────────────────────┐
   │ 方式一 · 共享源      │                        │ 方式二 · 本地构建         │

   │                     │                        │   └ VS/SDK → 仅检测+指引  │
   │                     │                        │ ② verify-compat.cjs     │
   │                     │                        │ ③ 构建（旧 .bat 流程）    │
   │                     │                        │ ④ serve-feed.cjs        │
   │                     │                        │ ⑤ 本地 feed → 检查更新    │
   └──────────┬──────────┘                        └────────────┬────────────┘
```

| **P4** | 环境预检接入 | P1 | 预检结果与实测一致 |
| **P5** | 兼容性校验 + 诊断包 | P4 | 人为改锚点，验证 fail loudly + 报告可读 |
| **P6** | 方式二打通（本地 feed） | P4 | 本地构建 → 本地 feed → 装上 |
| **P7** | 更新面板 UI（客户端插件） | P3/P6 | 两种模式在 UI 上都能走通 |
| **P8** | 引导式修复闭环 | P5 | VS/SDK 缺失时给出可执行指引 |

**建议先把 P2+P3 做完**——投入最小，收益最直接（你现在那个包「检查更新」是死的），而且能把"下载→停任务→退出→装→重启"这条最容易出事的链路先用官方代码验证一遍。
